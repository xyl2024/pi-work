# 语音输入在浏览器采集并编码 WAV，由服务端持 DeepSeek key 转写

聊天输入框要加**语音输入**：录音交给 DeepSeek 的 ASR 接口**转写**，文本落到光标处。三处选择都不是显然的，记在这里。

**浏览器产出 WAV，服务端不转码。** DeepSeek ASR 只接受 16 位 PCM WAV 与 Ogg Opus，单次 ≤8 MiB、≤120 秒。Chrome 的 `MediaRecorder` 不出 `audio/ogg`（只有 `audio/webm;codecs=opus`），所以走 `MediaRecorder` 就必须在服务端挂 ffmpeg 转码，给 Pi Work 引入一个原生依赖和一条新的部署约束。改用 `getUserMedia` + `AudioWorklet` 直采 PCM，用 `AudioContext({ sampleRate: 16000 })` 让浏览器重采样，自己拼 16 kHz 单声道 16 位 WAV：120 秒约 3.8 MB，仍在 8 MiB 以内，且 48 kHz 会直接撞上 11.5 MB 的体积上限。代价是要自己写几十行 WAV 头封装和一个录音器 module——纯逻辑，容易测。

**转写走服务端，浏览器不直连 DeepSeek。** 与「模型请求全部经服务端」一致：key 只在服务端，浏览器既不该拿到 key，也不该被 CORS 绑在 DeepSeek 的跨域策略上。这对语音输入尤其要紧——语音输入默认从手机/局域网打开，那边的浏览器配置完全不由我们控制。

**复用 `~/.pi-work/deepseek/api-key`，不新开第三个密钥面。** 仓库里已经有两套 DeepSeek key：pi SDK 管的 `~/.pi/agent/auth.json`（模型 provider）与 pi-work 自己的 `~/.pi-work/deepseek/api-key`（网页搜索/抓取工具）。转写是 pi-work 的工具能力而不是模型 provider，因此跟后者走，DeepSeek Key 那一行备注「共用此 key」。把第三个密钥塞进模型 provider 只会让「哪个 key 管什么」更难讲清。

**文本落点是光标处，绝不自动发送。** 转写必然有错字，用户必须有机会改。语音输入是输入方式，不是命令通道；这条边界决定了后面不会长成「语音直接发消息」。

**取消即丢弃。** Esc、切会话、组件卸载、录音中触发发送，都取消当前语音输入并中止在途请求，迟到响应不得写回输入框。录音是叠加态：不锁输入框、不禁用发送、不禁用快捷键。

**按钮只靠图标与动画说话。** 三态（空闲麦克风、录音中的红点 + 计时 + 电平、转写中的 spinner）都在发送按钮左侧那一个圆里表达，按钮内零说明文字。失败时在输入框上方给一行中性提示：每类失败一条，由稳定错误码映射，绝不透传上游原文。

## Considered options

- **`MediaRecorder` + 服务端 ffmpeg。** 前端代码最短，但换来一个原生依赖、一条部署约束（桌面轨道要按 Windows 打包），以及一段「上传 webm 再转成 wav」的纯浪费。既然 ASR 上限只有 120 秒，前端自己编码更划算。
- **前端 wasm 编码器（webm→ogg/opus）。** 几百 KB 的打包体积换一个本可以避免的解码步骤，且在 `AudioWorklet` 已经能拿到裸 PCM 的情况下毫无必要。
- **浏览器直连 DeepSeek（自带 key 或临时 token）。** 少一跳，但把 key 暴露给前端、把可用性交给 CORS，并且与既有「服务端代理一切第三方调用」的形状不一致。
- **按 DeepSeek 原样计 120 秒硬截断，不做 <500 ms 判定。** 每次误点都发请求、都计费，还会因空文本产生一次「失败」提示。
- **长音频分段连续请求。** 120 秒对一句话绰绰有余；分段会带来切词、多次计费和 429 并发上限的一整套边界。
- **把转写做成模型 provider 的另一种能力。** 它没有模型、没有会话、没有工具循环，只是文件进文本出，塞进 provider 抽象只会让两边都变形。

## Consequences

- 服务端只做无状态转发与错误映射，不认识音频格式的细节；音频合规性由前端保证，服务端仅把上游 400/413 转成中性错误码。
- 前端必须自带一个录音器 module（采集、重采样、停止、释放）与一个 WAV 封装纯函数；两者都可脱离真麦克风测试。
- 语音输入要求安全上下文：明文 HTTP 的局域网部署下 `getUserMedia` 恒不可用，因此按钮按能力探测渲染，不做提示也不做绕过。
- 计费口径是音频时长，不是成功次数；<500 ms 不发请求既是体验也是成本决策。
- 转写能力绑死 DeepSeek 一家，换 provider 要改服务端这一层；当前不抽象成多 provider（见 `.scratch/voice-input/spec.md` 的 Out of Scope）。
