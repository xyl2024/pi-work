# 记忆的写入交还通用工具，专用 memory 工具与三道防线整体移除

旧记忆机制（ADR-0029/0031/0038）里，agent 经专用 `memory` 工具写双库条目，写入路径上立扫描、预算、漂移三道防线，人另有一套记忆主视图与条目 API 作为并列写路径。**我们决定**：专用工具、双库、三道防线、记忆主视图、快照行与全部条目/用量 API 一并删除，agent 改用 bash / read / write / edit 这些通用工具直接读写 `~/.pi-work/memory/` 下的 Markdown 文件——记忆的写入路径不再是产品代码，而是 agent 本来就会用的文件系统能力。

## 为什么敢整体移除防线

三道防线防的威胁模型是「工具调用产生的内容会被原样送回所有会话的提示词前缀」（ADR-0029 的核心担忧），这个担忧本身仍然成立，移除的是代码层防护，不是接受注入。判断依据：

- **信任 agent**。记忆本就是 agent 自主维护的内容，防线拦的是「agent 自己写坏」；把组织记忆的规则写进注入的**记忆管理指引**（指引承担原防线里的预算约束、写入后同步索引等约定），agent 有通用智能按指引行事。用户如果连 agent 在自己的记忆目录里写什么都信不过，那 bash 工具早已给出更大的破坏面，防线在信任边界上本就站不住。
- **零代码防护的收益在删不在留**。旧实现是 `lib/shared/memory.ts`、`memory-store.ts` 共近千行加三份测试；扫描误伤正常内容（「不要告诉用户」这类句子）、漂移闸门整库卡死（ADR-0031 的起因）这类事故的成因是防护本身。
- **并发与有害内容靠指引与既有机制约束**。多会话并发写同一目录不做文件锁，靠指引提醒冲突可能；有害内容不做出库前扫描，注入面的大小由索引预算（2000 字符）天然压住，明细只在 agent 主动读取时进入单个会话的上下文，不再无条件站进所有会话的最前排。

人这条并列写路径随之消失，不再需要「用户写不过扫描」的特例论证（ADR-0038）：用户直接用文件系统或让 agent 改，文件的作者从始至终只有一层信任。

## Consequences

- `memory` 工具不再注册；子代理档案工具集少一个可选项。
- 记忆数据仍是全局一份；cwd 开关只控制注入与否。
- 旧双库数据由服务启动时的一次性迁移转为分类明细并生成索引，旧文件归档 `.bak`。
- 参见 ADR-0052（两级注入语义）。
