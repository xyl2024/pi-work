# 助理对话是跨会话虚拟时间线，而非单会话 + compaction

个人助理在界面上是一条永不换段的聊天记录。用户在助理页发出的每条消息、收到的每条回复，都在同一条时间线上；向上滚动可以一直翻到最早的那句话。数据层却不是一条记录：每个助理会话仍是普通 pi 会话（JSONL），默认 cwd 下会不断出现新的、带 `pi_work_assistant_session` 标记的会话文件。

决策是：**助理对话不是某一个会话，而是默认 cwd 下全部带助理标记的会话按创建时间排序、拍平成的一条虚拟时间线。** 会话边界只存在于文件与列表接口里，助理界面按可见消息连续分页，每页 50 条，跨会话取满一页，不插入任何分隔、标题或「上一段对话」提示。投影由共享纯模块 `lib/shared/assistant-conversation.ts` 完成，界面与测试都只面对拍平后的消息序列。

## Considered options

- **一条助理会话攒到底，上下文满了就 compaction。** 这是最省事、也最贴近现有编码会话的做法：不需要跨文件读取，不需要排序与分页，界面直接复用单会话时间线。代价是助理对话被 pi 的压缩机制改写：上下文接近上限时，旧消息被总结成一段摘要，原始短句消失，向上翻历史翻到的不是当时说过的话，而是模型的转述。个人助理的核心承诺是「历史永远连续」，压缩会直接违背它。
- **每次上下文将满时新建会话，由模型生成一段交接总结。** 这是终局方向，但第一期不做：它需要跨会话总结、150k 阈值、总结缓存与失败重试，复杂度远高于本期要解决的问题。虚拟时间线不需要这些机制就能先让历史连续。
- **把助理对话单独存成一份消息文件，不再用 pi 会话。** 能彻底摆脱会话边界，但等于另起一套存储，发送、流式、落盘、刷新恢复全部要重写，违背「助理会话在数据层就是普通 pi 会话」的实现决定。
- **只在界面隐藏会话边界，不改变分页单位。** 视觉上连续，但每页仍按会话切分时，一页可能只有 3 条消息，或把一次对话从中间截断；用户会感到翻页节奏由看不见的文件边界决定。

## Consequences

- 会话边界对用户不可见，但对实现可见：投影必须先按 `created` 排序再拍平，顺序错一次用户就会看到「回复早于提问」；排序与过滤因此成为纯模块测试的第一组用例。
- 分页单位是可见消息而不是文件。一页 50 条可能横跨两个甚至三个会话，这是预期行为；分页接口只暴露消息与 `hasMore`，不暴露会话 id。
- 读取侧需要把默认 cwd 下所有带标记会话的消息都取出来。第一期由 `GET /api/assistant/sessions?includeMessages=1` 一次返回，投影在客户端完成；会话数量增长后，这个接口会成为首个需要服务端游标分页的地方，但投影模块的输入输出形状不需要变。
- 旧消息不会被 compaction 改写，因此助理会话的 JSONL 会单调增长，磁盘占用高于「单会话 + 压缩」路线。这是用存储换历史真实性的明确取舍；等到交接机制落地，关闭一段会话的成本会从「压缩」变成「换文件」。
- 助理界面不能复用 `buildChatTimeline` 的会话内索引映射，它需要的是跨会话的连续可见索引；两者共享 `isVisibleChatMessage` 这一可见判据，但时间线语义不同。
- 这个决定很难回退：一旦用户习惯了连续历史，再引入会话边界或压缩摘要，就会丢失他们已经翻到过的原始消息。也正因为如此，界面、接口与测试都不应依赖「当前只有一个助理会话」这个偶然事实。
