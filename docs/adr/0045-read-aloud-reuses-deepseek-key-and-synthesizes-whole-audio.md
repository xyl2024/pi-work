# 朗读复用 DeepSeek 密钥面、整段非流式、单例播放器

聊天回答要加**朗读**：每条回答的操作栏里点一下，服务端用 DeepSeek 合成整段音频，浏览器播放。三处选择不是显然的，记在这里。

**复用 `~/.pi-work/deepseek/api-key`，不新开第三个密钥面。** 合成是 pi-work 的工具能力（网页搜索/抓取、语音转写、朗读），不是模型 provider，因此跟语音转写共用同一把 key 与同一个设置项，不写进 pi SDK 的 `~/.pi/agent/auth.json`。理由与 ADR-0044 同源：把第三个密钥塞进模型 provider 只会让「哪个 key 管什么」更难讲清。代价是 DeepSeek key 一旦撤销，搜索、转写、朗读一起失效——这本来就是同一家服务商的同一把凭证，用户不需要为它们各配一次。

**整段非流式：先合成完，再播放。** 上游返回的是二进制音频流，但 chunked WAV 的头部长度字段不可靠，边下边播在不同浏览器上行为不确定。选择等完整文件，代价是长回答点击后要等几秒才出声；换来的是播放器只面对一段确定的音频，blob URL 的生命周期与失败判定都只有一种形状。URI 里不出现回答文本：合成请求是 POST，文本只在请求体里，客户端拿到的是音频二进制，不接触上游地址、鉴权与错误形状。

**播放器是单例客户端模块，不是组件 state。** `lib/client/read-aloud-player.ts` 持有唯一一个音频元素与 blob URL，暴露播放/停止/订阅，组件只订阅「当前这条是否在播 / 是否在合成」。这样「同一时刻只有一条声音」由模块保证，消息组件之间无需互相通知；切换会话时只需调用一次 `stop()`。代价是播放状态脱离 React 生命周期，模块必须在停止、切换、播完三处显式释放 URL，否则会泄漏 blob。

## Considered options

- **浏览器直连 DeepSeek（或按需下发临时 key）。** 少一跳，但把 key 暴露给前端，把可用性交给 CORS，并且与既有「服务端代理一切第三方调用」的形状不一致。
- **流式合成、边下边播。** 首字延迟更低，但要求解析不可靠的 WAV 头、处理中途断流的半段音频，播放器要维护一套 chunk 队列；当前回答长度下收益不足以抵消复杂度。
- **把播放状态放进每条消息组件的 `useState`。** 每条消息都要知道别人是否在播，必须互相喊话或抬到共同父级；单例模块把这条约束收进一个地方，组件只剩渲染。
- **在组件里 new `Audio` 并手动管理 URL。** 同一段逻辑会在每条消息里复制一遍，且「切另一条时停掉前一条」需要跨组件协调。
- **新开一个朗读专用 DeepSeek key / 设置项。** 多一个配置面、多一处「该填哪个」的困惑，换不来任何隔离收益。

## Consequences

- 朗读能力绑死 DeepSeek 的合成接口；换供应商要改服务端 `synthesize` 通道与共享错误码，前端不动。
- 计费字符上限（10,000，汉字计 2）与默认音色（`stella`）集中在 `lib/shared/read-aloud.ts`，数值来自 DeepSeek 官方文档，将来修正只改一处。
- 服务端只在进程内直转上游；按内容寻址的合成缓存与同键并发合并是后续工作，不改变本 ADR 的三条形状。
- 播放失败统一给一句中性提示，并按稳定错误码映射；上游原文只进服务端日志。
- 朗读文本只走 POST 请求体，URL、日志与浏览器历史里不出现回答内容。
