# 定时任务未读角标：本机时间线 + 服务端计数

定时任务是后台跑的：结果在用户不看面板的时候产生，而侧边栏「定时任务」这一行原先只有一个「运行中」圆点，跑完之后什么都不留。我们决定在这一行加未读计数，形如 `定时任务  ●  [3 | 1]`：左边是运行中脉冲点，右边是一个分段胶囊，左段是成功数，右段是失败数（失败单独可见，不混进总数）。

「未读」没有唯一的自然定义，必须先选一个基线。我们决定：

- **基线是本机时间戳**：`localStorage["pi-work/scheduler-unread-seen-at"]`。进入定时任务主视图时写入当前时间，离开时再写一次，因此「看过的」包含整个停留期间结束的 run。
- **计数在服务端做**：`GET /api/scheduled-tasks/unread?since=<ms>` 由 `countUnreadRuns(since)` 对 `task_runs` 按 `status` 分组统计，只统计 `ended_at > since` 的已结束 run。
- **计数单位是结果条数**，不是任务条数：一个任务连跑三次就是三条未读。
- **超时与中断算失败**：`isSchedulerRunFailure` 只把 `success` 与 `running` 排除在外。
- **首次使用没有基线**：第一次读取时把 seen-at 初始化成「现在」，历史 run 全部视为已读，避免第一次打开就冒出上百条。
- **客户端每 60 秒轮询一次**，页面重新可见时立刻补一次；角标只在侧边栏挂载期间轮询。

## Considered options

- **服务端保存 seen-at（每个用户 / 每个任务）。** 跨浏览器一致，但要在 `scheduler.db` 里加一张已读表或写进 `~/.pi-work` 的配置文件，还要处理多端互相覆盖；Pi Work 目前是单用户本机应用，换来的复杂度没有对应收益。
- **按任务记录已读（每行一个点）。** 信息更细，但侧边栏这一行变成「有几个任务有新东西」，用户真正关心的是「有几条结果没看」；逐任务点还会和「运行中」圆点在同一行里抢注意力。
- **进入面板即清零、不区分成功失败。** 简单，但失败要等到打开面板才被发现，而这正是后台任务最需要提前暴露的部分。
- **把计数塞进 `/api/scheduled-tasks` 的轮询里。** 那个轮询只在面板打开时跑，面板关着时角标就不会更新，正是角标最需要工作的时候。

## Consequences

- 未读状态是本机的：换浏览器或清 localStorage 会重新建立基线，第一次基线之前的结果不计入未读。
- `task_runs` 上按 `ended_at` 分组统计走的是已有索引（`task_id, started_at`）之外的一次全表扫描；历史规模有限（每个任务默认最多保留 50 条 run），可接受。若 run 表未来无界增长，需要补 `ended_at` 索引。
- 停留在面板期间新结束的 run 会立刻被下一次进入 / 离开时的 seen-at 覆盖，所以「在面板里看着它跑完」不会留下未读。
