# Turn execution has one seam, and waits for `agent_settled`

Four call sites independently implemented "start a session → send the prompt → wait for the terminal event → record the outcome": `lib/server/kanban/runner.ts`, `lib/server/scheduler/runner.ts`, `lib/server/wechat/inbound.ts`, and `lib/server/subagent-tool.ts` (`waitForAgentEnd`). No helper was shared — each carried its own copy of the `MaxLifetimeExceededError` / `SessionInterruptedError` classes, its own terminal-event listener and its own final-assistant-text extraction, with hand-copied comments ("Mirrors `lib/server/wechat/inbound.ts:waitForAgentReply`", "Install the terminal-event listener before dispatching the prompt").

The copies had already drifted, and three of the drifts were bugs rather than taste. The three background runners listen for `agent_end`, but the pi RPC docs define `agent_end` as "one low-level agent run completes (may still be followed by retry, compaction, or queued continuations)" and `agent_settled` as "no automatic retry, compaction retry, or queued continuation remains" — so they could declare a run finished while pi was still going. The wechat path subscribed to events *after* awaiting the prompt, so a fast reply was missed and only the 5-minute timeout noticed; it also had no `onDestroy` handling, so a destroyed session hung until that timeout.

We decided a turn runs through one seam. `lib/server/turn/` exports `runTurn(spec)` — which performs session acquisition, model/thinking/tool setup, terminal subscription, prompt dispatch, classification and cleanup — plus `watchSettled(session)`, the inner seam for callers that only observe a turn rather than await it. **`agent_settled` is the terminal event; a turn is not over at `agent_end`.** The module classifies the outcome into a neutral `{ status: completed | aborted | failed | timeout | interrupted | cancelled, text, error?, stopReason? }`, and each caller maps that onto its own vocabulary (`review_test`, `success/error/timeout/interrupted`, a wechat reply, a cancelled subagent). Timeouts stay per-caller — passed as `deadlineMs` rather than unified — and the session acquisition policy ("fresh" vs "reuse an existing session id") is a spec parameter, since wechat is the only caller that reuses. Cancellation is likewise a caller-supplied policy: `abortSources` is a list of `{ signal, reason }`, and any one firing makes the module tell the session to abort and settle as `cancelled` — the turn really stops, it is not merely labelled.

The scheduler, kanban and wechat runners migrate in three separate slices; the subagent path is deliberately left for a later slice, because it additionally needs a result re-read from the JSONL, and its interface is designed to accommodate it (`deadlineMs` plus the raw `stopReason` are already in the neutral result; the stop sources and `cancelled` outcome it needs now exist as `abortSources`). The behavior changes in the migration slice are frozen to the three drifts above; the timeout values (2h / 2h-configurable / 5min / 15min), "an empty reply counts as success" in wechat, and "`aborted` has no state of its own" in kanban are product decisions recorded for a separate change, not silently settled by a move.

## Considered options

- **Leave the four implementations alone.** Smallest possible diff, but the knowledge keeps drifting: a fix to the terminal wait or the timeout policy has to be found and re-applied in four places, and two of them were already wrong.
- **Unify the product vocabulary in the same slice too** (one timeout policy, one answer for an empty reply, a real `aborted` state). Tempting, but it forces product decisions and a large code move into one diff, which makes "nothing else broke" impossible to confirm by reading.
- **Let the module only await the terminal event, leaving session acquisition to callers.** Keeps the module smaller, but re-copies the ordering knowledge that has to be right for the wait to work at all (subscribe before dispatch, set model/thinking before prompting) — the ordering is part of the turn, not of the caller.

## Consequences

- `agent_end` is still treated as terminal outside this module: the chat event stream (`hooks/useAgentSession/events.ts:175`), the kanban reverse-sync watcher (`lib/server/kanban/session-sync.ts:75`), the translate stream (`app/api/translate/route.ts:140`), the empty-reply log and turn-end session-notify delivery in `rpc-manager.ts:194,205`, and two callers that accept either event (`app/api/btw/send/route.ts:267`, `hooks/useBtw.ts:478`). The subagent path already uses `agent_settled` (`subagent-tool.ts:273`). Aligning the rest is a separate change with its own behaviour risk; this ADR does not claim they are correct today.
- `rpc-manager.ts` remains the seam that creates and disposes sessions; the turn module calls `startRpcSession` rather than reimplementing session acquisition, and does not own the session registry.
- Because the migration fixes three bugs, it is not a behaviour-frozen refactor: each slice's PR carries an explicit list of the intended behaviour changes, and the pure logic (terminal classification, text extraction) is unit-tested directly while the orchestration takes its session factory as a parameter so a fake session can drive the ordering and settle semantics.
- Timeouts are deliberately not centralized: a new caller must choose its own `deadlineMs`, and "what happens when a turn times out" (destroy the session, abort it, or leave it running) is still the caller's policy.
