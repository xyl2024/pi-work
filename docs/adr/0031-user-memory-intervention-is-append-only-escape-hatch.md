# 用户对记忆的直接干预是只减不增的漂移逃生阀

记忆文件是唯一真相，agent 通过 `memory` 工具经扫描、预算、漂移三道防线写入（ADR-0029）。但用户或外部程序绕过工具直接手改文件时，只要写进一段没有按 `§` 分隔的自由文本，某个条目就会长于整库上限，漂移闸门从此对**整库**拒绝写入，包括删除。V1 里用户唯一的修复方式是继续手改文件，而手改正是产生漂移的原因：记忆系统可能永久卡死，用户既不知道发生了什么，也没有可用工具自救。

> 本篇的「只减不增」边界已由 ADR-0038 修订：记忆管理现在允许用户新增与原地编辑，删除路径本身不变。

**我们决定**：给用户一条与 `applyMemoryOperations` 并列的删除入口。它复用同一把 `.lock`、锁内重读与 `writeFileAtomic`，但**不经过漂移闸门，也不经过扫描与预算闸门**，因为它的能力被刻意限定为「只减不增」——任何一次成功删除都让记忆库更接近可解析状态，不可能引入污染或膨胀。

## 为什么人拿到比 agent 更窄的写路径

agent 的写入会把内容送进下一个会话的系统提示词前缀，所以入口必须过注入/外泄扫描；用户手写的正常句子却可能被同一套中文注入正则误伤（例如「不要告诉用户」这类正常表述）。让用户走同一条含扫描的路径意味着把「用户输入是否该过扫描」这个尚未回答的问题提前落地；只在面板里开放删除则绕开了它。新增与原地编辑明确留在本期范围之外，等扫描的输入来源有了答案再谈。

窄路径同时改变威胁模型：agent 能无限次追加并膨胀记忆库，人只能让库变小。于是人的路径不需要预算、不需要扫描、也不需要「批量只看终态」那套整合规则。

## 漂移死锁的解开方式

漂移闸门位于操作执行之前，任何操作（包括删除）都被整库拒绝；这就是「面板能删」不是加个按钮的原因。用户删除路径因此是一条绕闸门但复用锁与原子写的独立函数：

- 不做漂移闸门：面板存在的意义就是删掉那条超长手写文本；
- 不做预算闸门：删除后即便 `used` 仍超上限也照常写入，删除永不因预算被拒；
- 不做内容扫描：路径上没有新内容入库，没有需要扫描的输入。

agent 路径的三道防线与冻结快照一分未变（ADR-0029 不改）：漂移态下 add / patch / remove 仍被整库拒绝，agent 不能借用户入口绕过闸门。

## 索引加哈希的钉扎

面板是长驻的，另一个会话的写入会让索引整体位移，而删除不可撤销。所以客户端带上渲染时算出的条目哈希，服务端在锁内重读后先查索引范围（越界返回 `out_of_range`），再比对哈希（不匹配返回 `stale_entry`），两者都保持文件不变。索引单独不可靠，哈希单独无法定位重复文本；两者合起来才表达「用户看到的那一条，就是服务端要删的那一条」。

## 只有超长条目留 `.bak`

超长条目是「外部手写的自由文本」信号，也是唯一一种在面板上被截断展示、且删除后可能让人后悔的数据。删除它之前独占创建一份 `.bak`，文件名带 Unix 秒时间戳、冲突时加 `NN` 序号，内容为删除前的完整原文。普通条目删除不备份：它已在面板完整显示、又经过确认弹窗，不是不可见的数据损失；给每次删除都备份只会让用户数据目录堆满垃圾。

## Considered options

- **让用户走 `memory` 工具的同一条写入路径**：把扫描的输入来源问题与删除需求绑在一起，正常用户句子可能被误伤，还会让人的路径继承预算与批量语义。
- **面板里同时开放新增与编辑**：先要回答用户输入是否过注入扫描；删除没有这个问题，本期只做删除。
- **漂移态下整库仍然拒绝删除，只给用户诊断信息**：那等于把自救推回手改文件，而死锁的成因正是手改。
- **每次删除都备份**：备份文件无界增长，且普通删除已经过完整展示与确认，备份收益低于目录垃圾成本。

## Consequences

- 用户删除成功返回写后快照，面板原地刷新条目与用量。
- 删除超长条目后的成功反馈额外说明「记忆库恢复可写」。
- `.bak` 是一次性快照，不是撤销或历史栈；恢复仍需用户自己处理文件。
- 用户直接干预的删除能力保持原样；新增与编辑由 ADR-0038 扩展。
