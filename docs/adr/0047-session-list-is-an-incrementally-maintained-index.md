# 会话列表由文件签名增量维护的索引提供

首页的会话列与工作区列表读同一份「会话元数据」：id、cwd、名字、首条消息、创建/修改时间、父会话、助理标记。这份元数据以前每次请求都从磁盘重算——遍历 `~/.pi/agent/sessions` 下每个 JSONL，同步读文件头直到拿到首条消息（最多 1 MB），再读 3000 多个名字 sidecar 与四百多个权限 sidecar，最后用 5 秒 TTL 的缓存兜一下。

在真实数据上（4763 个会话、1.16 GB）这套做法是 6 秒级的同步扫描：事件循环被占满，首屏所有接口一起排队；5 秒 TTL 一过就整份重演，所以不是「只慢一次」。名字那一项尤其贵——为了一个可能写在文件任意位置的 `session_info`，几乎每个文件都要读到头。

**决策：会话元数据由一个长期索引提供，索引按文件签名（mtime + size）增量对齐。** 每次刷新只做一层 `readdir` 与一次 `stat`：签名没变的文件直接复用索引里的 header，不再读一个字节；新增或变化的文件才重读。时间不再是新鲜度的依据，缓存里没有「过期」这个概念——只有「这个文件我见过没有、变过没有」。因此删除 5 秒 TTL，`invalidateSessionListCache()` 也不再是「丢掉整张表」，而是丢掉 sidecar 派生数据（名字缓存）；文件本身的变更靠签名发现。

**名字优先来自 sidecar，其次才是文件。** pi-work 自己在改名、自动起名时都会把名字写进 `session-names` sidecar，pi 自己改名的事件也被镜像进去。所以只有 sidecar 没有名字时才去文件里找，且从句尾往回按 64 KB 读，找到最后一条 `session_info` 就停，最多 64 KB。头部窗口仍然负责 id、cwd、首条消息与助理标记，行为与旧实现逐步对齐（含「跳过超大系统提示条目找首条用户消息」「图片首条消息算空标题」）。

**索引落盘并原子替换。** 文件写进 pi-work 数据目录，带版本号与 agent 目录标识；进程重启时先加载它，再做一次签名对齐，于是重启只花一次 stat 的时间而不是一次全量扫描。读到版本不符或坏 JSON 时静默丢弃并重建——索引是缓存，不是真值。

**刷新全程异步、按固定并发度。** 读文件走文件系统 promise API，并发 16/32，事件循环不再被占住，首屏其它请求（会话详情、状态栏、运行中标记）正常返回。这在真实数据上把冷启动的同步阻塞换成 2.3 秒的后台异步扫描（启动预热已经跑掉了），稳态刷新约 200 毫秒。

**搜索复用同一份元数据。** 搜索以前为了给命中结果补元数据而走「解析全部会话文件」的入口（8.4 秒），现在元数据来自索引，逐行流式读只发生在关键词命中的候选文件上。

## Considered options

- **保留 5 秒 TTL，只把扫描改快。** 改快之后每次扫描仍然要做全部工作，只是把 6 秒压到 2 秒，而且 5 秒一到就再来一次——用户还是会在刷新页面时撞上扫描窗口。
- **缓存按目录 mtime 判断整目录是否变化。** 会话文件是追加写的，目录 mtime 只在增删改名时变动；拿它当新鲜度会让「刚聊完的会话没有跳到列表顶部」。签名必须落到文件一级。
- **只靠 `fs.watch` 驱动刷新。** 监听递归目录在部分平台不可靠，也挡不住进程启动时的一次对齐；签名对齐本身是幂等的，watch 只可能作为将来的额外优化。
- **把索引做成 SQLite。** 索引只是一张「路径 → header」的表，落盘用 JSON 原子替换已经够用；引入一张表反而要为它对并发与迁移负责。
- **用 pi SDK 的 `SessionManager.listAll()`。** 它会完整解析每个会话文件，本机实测 8.4 秒，且拿不到我们需要的助理标记与首条消息口径。
- **stat 改成同步以降低延迟（本机 21 毫秒 vs 异步 155 毫秒）。** 异步版本慢在 Node 默认 4 个线程池线程，但它不阻塞事件循环，而阻塞正是这次要治的病；200 毫秒的异步刷新可以接受，21 毫秒的同步阻塞不行。

## Consequences

- 会话元数据的真值仍在磁盘上的 JSONL 与 sidecar 里；索引只是派生物，删掉它只会让下一次刷新变慢，不会丢任何东西。
- 新鲜度语义变成「下一次列表请求一定反映当前目录」，不再有「5 秒内看到旧列表」的窗口。代价是每次列表请求都会 stat 一遍目录里的文件（本机约 200 毫秒、后台异步）。
- 文件名字只在句尾 64 KB 内被搜索。更早的 `session_info`（长会话中途改名）不会从文件里读到，此时名字来自 sidecar；两个来源都没有就回退到标题回退链。
- 新增一类需要维护的「旁路缓存」：名字 sidecar 与权限 sidecar 各自按目录签名缓存，写入路径必须显式失效。两者都已在写入与删除处调用失效。
- 会话列表与搜索结果的 `messageCount` 在 header-only 路径上为 0；需要精确消息数的路径（会话详情）仍走完整解析。
- 刷新期间并发到达的列表请求共享同一次对齐（in-flight），而不是读一份旧快照：会话详情的路径解析依赖「刚创建的会话已经在索引里」，读旧快照会让它 404。
- 启动预热挂在既有的 file-access bootstrap 上，进程起来后立刻在后台做一次对齐；落盘索引就绪后，重启的第一次对齐只花 stat 的时间（本机约 270 毫秒）。
- 名字 sidecar 与权限模式 sidecar 的目录签名缓存共用一个 `directorySignature` 帮手；两者的写入与删除路径都必须显式失效，新增同类 sidecar 时照此办理。
- 索引文件的格式与位置是内部约定，不承诺向后兼容；版本号变化即重建。
