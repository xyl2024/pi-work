# 服务端模型调用指标：TTFT、平均生成 TPS、全程 TPS

Status: ready-for-agent

## Problem Statement

Pi Work 用户希望知道模型多久开始输出、开始输出后有多快，以及包含等待时间的整次调用有多快。目前聊天界面的 `t/s` 通过字符数除以 4 估算 token，再除以浏览器观察到的流式时间；中文、思考和工具参数都会影响结果，完成后也没有可查询的最终指标。

现有审计数据不能完整回答这些问题。LLM API 审计按实际 HTTP 请求记录到响应头的耗时，并非首个有效输出延迟；Token 审计已有最终 usage 和部分调用耗时，但缺少首尾有效输出时间，而且当前采集入口不能统一覆盖翻译、自动起名和压缩等业务调用。用户不能据此可靠分析单次模型调用的表现。

## Solution

在服务端按一次逻辑模型调用采集时间与最终用量，持久化 TTFT、平均生成 TPS、全程 TPS 所需的事实，通过现有审计 API 查询逐次调用结果。

覆盖全部现存业务模型调用，区分业务来源；排除设置中的模型连接测试。一次调用内部的请求重试和退避属于同一条记录，工具执行后再次请求模型属于另一条记录。三个指标统一使用服务端观测口径，不受浏览器渲染和会话事件传输影响。

最终 token 数使用服务商经 SDK 返回的输出 usage。无法可靠计算的值返回 `null`，同时保留终态与已知事实。本次交付只包含服务端采集、存储、逐调用查询，不接入聊天界面或审计面板视图，也不提供性能汇总。

## User Stories

1. 作为 Pi Work 用户，我希望知道一次模型调用的 TTFT，以便判断模型多久开始返回有效输出。
2. 作为 Pi Work 用户，我希望知道一次模型调用的平均生成 TPS，以便了解开始输出后的平均吞吐。
3. 作为 Pi Work 用户，我希望知道一次模型调用的全程 TPS，以便了解包含等待与收尾的实际调用表现。
4. 作为 Pi Work 用户，我希望最终 TPS 使用服务商报告的输出 token 数，以便避免字符估算对中文等内容产生的误差。
5. 作为 Pi Work 用户，我希望正文、思考和工具参数都能作为有效输出，以便纯工具调用也能测得首输出延迟。
6. 作为 Pi Work 用户，我希望响应头、心跳、空增量和内容块声明不被视为 token，以便 TTFT 不被提前记下。
7. 作为 Pi Work 用户，我希望同一个口径覆盖聊天调用，以便检查日常使用时的模型表现。
8. 作为 Pi Work 用户，我希望同一个口径覆盖子代理调用，以便查看子代理实际使用模型的表现。
9. 作为 Pi Work 用户，我希望同一个口径覆盖定时任务调用，以便分析后台回合的模型耗时。
10. 作为 Pi Work 用户，我希望同一个口径覆盖频道和微信入站消息触发的调用，以便后台消息入口不会漏记。
11. 作为 Pi Work 用户，我希望同一个口径覆盖上下文窗口压缩与分支摘要调用，以便会话维护所使用的模型也可观测。
12. 作为 Pi Work 用户，我希望同一个口径覆盖翻译调用，以便辅助功能的模型表现也可查询。
13. 作为 Pi Work 用户，我希望同一个口径覆盖自动起名调用，以便一次性模型请求不会被遗漏。
14. 作为审计 API 使用者，我希望记录带有业务来源与调用用途，以便区分聊天、压缩、翻译和自动起名等调用。
15. 作为审计 API 使用者，我希望每条记录带有服务商、模型和可用的会话关联，以便定位调用属于谁。
16. 作为 Pi Work 用户，我希望调用内部的重试与退避计入实际等待，以便指标反映我承担的延迟。
17. 作为 Pi Work 用户，我希望工具执行后再次请求模型产生独立记录，以便工具耗时不会混进模型调用指标。
18. 作为 Pi Work 用户，我希望最后输出后的 usage 与终止事件等待只影响全程 TPS，以便生成窗口与收尾窗口保持明确区别。
19. 作为 Pi Work 用户，我希望失败和取消的调用仍然留下记录，以便排查为什么没有得到完整回复。
20. 作为 Pi Work 用户，我希望失败或取消后不出现正常完成调用的 TPS，以便不把部分输出误当作可比较的完整样本。
21. 作为 Pi Work 用户，我希望取消前已测得的 TTFT 得以保留，以便仍能知道调用何时开始输出。
22. 作为审计 API 使用者，我希望没有 usage 时 TPS 为 `null`，以便不会把缺失数据当作零输出。
23. 作为审计 API 使用者，我希望真实报告的零输出与未报告用量可以区分，以便正确解释结果。
24. 作为审计 API 使用者，我希望单输出块、零耗时和缺少有效输出的调用不产生无穷大或伪造的生成 TPS，以便下游可以安全处理这些记录。
25. 作为审计 API 使用者，我希望能按既有时间范围和会话条件分页查询记录，以便逐条检查调用而无需新增界面。
26. 作为 Pi Work 用户，我希望并发会话与并发子代理的指标互不混用，以便查询到的时间和 token 属于同一次调用。
27. 作为 Pi Work 用户，我希望会话事件重连、重放和重复收尾不会产生重复记录，以便调用次数保持可信。
28. 作为已有安装的用户，我希望数据库升级保留旧记录，并明确历史指标缺失，以便升级后仍能查询原有审计数据。
29. 作为 Pi Work 用户，我希望指标采集不改变回复、工具调用、重试或取消行为，以便性能观测不干扰实际使用。
30. 作为 Pi Work 用户，我希望指标采集不额外保存正文、思考和工具参数，以便只记录计算指标所需的元数据。
31. 作为审计 API 使用者，我希望明确隐藏思考与网络分块对生成 TPS 的限制，以便不会将它误解为可见文字速度或服务商内部解码速度。
32. 作为维护者，我希望通过受控模型输出和隔离存储验证最终 API 数据，以便不用真实付费模型或真实用户数据就能验收功能。

## Implementation Decisions

1. **统计单元是逻辑模型调用，不是回合或 HTTP 尝试。** 从服务端向模型运行时发起一次生成操作开始，到该操作返回最终结果、失败或取消结束。会话准备、模型选择、工具执行和等待下一次调用不计入。SDK 在这次生成操作内部执行的请求重试、退避计入同一次调用；上层在操作结束后重新发起生成，是新调用。一个回合可以包含多次调用。

2. **统一服务端采集边界。** 优先扩展已有模型运行时包装能力，让持久化会话、无磁盘会话及 SDK 内部压缩/摘要走同一套采集规则。不能只订阅聊天会话的助手消息完成通知，也不能只依赖全局 HTTP fetch 拦截：前者漏掉部分业务路径，后者缺少逻辑调用边界、统一 usage 和传输无关的输出语义。具体包装方式必须兼容 SDK 的流迭代和最终结果读取方式，不额外消费或抢走业务调用方的输出。

3. **覆盖现存业务入口。** 包括用户聊天、子代理、定时任务、频道/微信调用、手动与自动压缩、分支摘要、翻译及自动起名。实现前枚举实际调用入口并核对其接入统一采集边界；不以旧代码中残留的来源枚举推断某项功能仍存在。不恢复已移除的业务功能。

4. **来源与用途分开表达。** 保留用户、子代理、定时任务、直接调用等来源信息；补充足以区分聊天、频道消息、压缩/摘要、翻译和自动起名的用途元数据。用途不明时如实标记未知，不因缺少持久化会话而把调用丢弃，也不把新来源静默转换成用户聊天。已有会话关联可用时保留，不要求为辅助调用创建真实持久化会话。

5. **时间基准。** 调用开始、有效输出和终态之间的耗时使用同一单调时钟。墙钟时间仅用于调用开始日期、排序和筛选。SDK 已提供的单调耗时可以在语义一致时复用；不能混用墙钟起点和单调时钟终点。SDK 消息时间戳表示请求开始，不是消息完成，相关既有错误注释应随涉及的代码修正。

6. **有效输出定义。** 只接受规范化输出中的非空正文增量、非空思考增量、非空工具参数增量。空字符串不算；包含空格的非空增量仍算实际输出，不通过去除空白改变语义。角色、块开始/结束、工具名称声明、心跳、usage、HTTP 响应头及完成事件本身不算有效输出。不用字符或 chunk 数估算实际 token 数。

7. **TTFT。** 首个有效输出到达采集边界的时刻减去逻辑调用开始时刻，API 字段为 `ttftMs`，单位毫秒。已经观测到首输出时，即使随后失败或取消也保留该值。没有有效输出时为 `null`。该名称沿用 TTFT，但实际可观测单位是首个携带有效输出的增量，而非单个 tokenizer token。

8. **生成窗口。** 首个有效输出到最后一个有效输出之间的间隔，API 字段为 `generationDurationMs`，单位毫秒。终止事件、usage 回报和连接收尾等待不扩大这个窗口。只有一个有效输出块时窗口为零，不能用调用完成时间代替最后输出时间；完全没有有效输出时窗口为 `null`。

9. **平均生成 TPS。** 正常完成且服务商输出用量有效时，`generationTps = outputTokens × 1000 / generationDurationMs`。生成窗口缺失、为零、为负或无效时，结果为 `null`。失败或取消时，即使有部分用量和正的生成窗口，结果仍为 `null`。不能用“全程耗时减 TTFT”替代生成窗口，因为那会把收尾等待混入分母。

10. **全程 TPS。** 正常完成且服务商输出用量有效时，`endToEndTps = outputTokens × 1000 / durationMs`，其中 `durationMs` 是本次逻辑调用从开始到终态的耗时，包含内部重试、退避、首输出前等待与末尾收尾。分母无效或不大于零时为 `null`；失败、取消或缺少有效输出用量时为 `null`。无需看到有效输出也可以计算全程 TPS，只要完成状态、实际用量与总耗时均有效。

11. **usage 的权威与缺失。** 使用服务商经 SDK 返回的最终 `usage.output`，不加入输入 token、缓存读取或缓存写入 token。它可能包含隐藏思考；不要再加一次 reasoning 用量。仅接受有限、非负的有效输出用量；真实报告的零允许得到零全程 TPS，生成 TPS 仍需满足有效窗口条件。缺失不能转换为零。检查 SDK 对 usage 的初始化和回报行为，不能仅凭最终对象存在默认的零字段就认定服务商报告了用量；无法确认时按缺失处理，并对该能力边界留下注明。

12. **结果与状态契约。** 逐调用响应增加稳定的 `callId`、明确的调用终态，以及 `ttftMs`、`generationDurationMs`、`generationTps`、`endToEndTps`。保留原有总耗时语义及实际可获得的用量、服务商、模型、API、来源、用途和会话关联。终态至少区分正常完成、失败、取消；历史未知状态不得假定成功。新增指标字段始终存在，不可用时显式为 `null`，不能返回 NaN、Infinity、空字符串或伪造的零。TPS 不在服务端截断为显示用小数位。

13. **持久化与兼容。** 复用现有 Token 审计的数据库、数据目录与环境变量覆盖机制，扩展逻辑调用事实的存储及逐调用查询；不引入独立数据库。存储需容纳无持久化会话、缺失用量、明确终态和新增时间字段。可以通过同库的附加记录保持原有计费用量数据的约束与语义，不强迫旧计费字段用零表达未知。持久化原始时间间隔与用量事实，查询时由统一规则派生 TPS，避免维护两套公式。

14. **既有计费统计兼容。** 统一指标采集与原有 Token 审计写入必须避免重复记录、重复计费。新增辅助调用的性能记录不能无意改变原有 summary 的统计口径；不借此扩展费用汇总的产品范围。逐调用查询合并旧记录与新指标时，一次真实调用只能返回一次。稳定调用标识不能只靠毫秒时间戳或按时间邻近匹配 HTTP 审计记录，并发同毫秒开始的不同调用不得碰撞。

15. **兼容迁移。** 数据库迁移可重复执行、保留旧行，并允许旧记录缺少新事实。历史 TTFT、生成窗口和两个 TPS 一律为 `null`，不从字符数、回合耗时或旧审计耗时反推。旧的总耗时和用量仍可查询。新的类型、行映射、数据库和路由必须同步支持 nullable 字段，避免读取时再把 `null` 转为零。不得读取或修改真实用户数据库来完成开发验证。

16. **查询接口。** 扩展现有 Token 审计逐调用查询，保持 `{ rows, total }` 响应形状、既有时间范围与会话筛选、分页参数和上限。新增字段通过这一接口返回，记录按调用开始时间倒序，同时间使用稳定次序；`total` 与分页使用同一组筛选条件。无会话关联的业务调用能出现在未指定会话的结果中。不新增按服务商、模型或来源的筛选参数，不增加性能汇总接口。本次不改变 LLM API 审计按 HTTP 尝试记录的口径或字段含义。

17. **去重、并发与生命周期。** 每次实际发起调用拥有独立的计时状态和标识，不能依赖共享可变的“当前调用”来关联增量和 usage。重复完成回调、会话事件重放或 SSE 重连不新增记录；进程内已知失败或取消也应完成记录并清理订阅和临时状态。进程被强制终止前未完成的调用不承诺恢复，不新增崩溃恢复机制。

18. **观测不得改变业务。** 包装层保持流式顺序、结果内容、工具输入、错误、取消信号与重试策略，不额外发起模型请求。不为指标持久化回复正文、思考内容或工具参数。审计存储失败不得让原本成功的模型调用失败，错误日志遵循现有脱敏方式。纯协议与计算规则不依赖 Node、SQLite 或 SDK；SDK 适配、计时与存储留在服务端。

## Testing Decisions

1. **主要验收边界：受控模型调用到审计查询结果。** 在进程内驱动已有模型运行时包装入口，底层提供可控的规范化输出流、最终 usage、错误及取消行为，使用可控单调时钟和真实临时 SQLite，最后以真实 Request 驱动逐调用查询的 route handler。断言 HTTP 状态、响应体、记录数量、时间、用量、终态与 nullable 指标。以这条最高可行边界覆盖采集、存储、映射和 API，避免分别 mock 每层后只验证实现相互调用。

2. **现有先例。** 模型连接诊断测试已经用受控模型运行时与输出流验证时序和取消；LLM 审计保留期测试已经使用临时 SQLite 和数据目录覆盖；桌面信任边界测试已经在进程内用真实 Request 驱动 route handler。复用这些测试组织方式，不引入浏览器或新的端到端框架。

3. **确定性公式样本。** 逻辑调用于 0 ms 开始，2,000 ms 首次有效输出，6,000 ms 最后有效输出，7,000 ms 完成，最终输出 120 tokens。查询应得到 TTFT 2,000 ms、生成窗口 4,000 ms、生成 TPS 30、全程 TPS 120/7。这个样本同时证明收尾的 1,000 ms 不进入生成窗口。只在数值精度要求处使用合理浮点容差，不依赖真实等待或付费请求。

4. **输出语义。** 分别覆盖首输出为正文、思考、工具参数；覆盖心跳、响应头、空增量、块声明不会提前开始计时，非空空白增量会计时。单个有效输出块的生成窗口为零且生成 TPS 为 `null`。没有输出但正常完成并有实际用量时，TTFT 和生成 TPS 为 `null`，全程 TPS 仍按规则计算。

5. **usage 与边界值。** 覆盖最终 usage 覆盖初始化占位值、未回报 usage、无效或负的输出用量、实际零输出、隐藏思考已计入 output、零全程耗时及无效时间事实。断言不存在重复累计 reasoning、字符估算、NaN 或 Infinity。纯公式边界若在主要验收边界驱动成本过高，才补少量直接规则测试，不以公式测试替代采集链路测试。

6. **重试与调用划分。** 一次逻辑调用内部先失败再重试成功，应只产生一条性能记录，TTFT 与全程耗时包含内部等待；逻辑操作结束后上层重新调用，产生另一条记录。工具执行前后的两次模型调用产生两条记录，工具执行时间不进入两者的耗时。性能记录不改变既有 HTTP 尝试审计粒度。

7. **失败与取消。** 覆盖首输出前失败、首输出后失败、调用中取消、部分 usage 后取消以及抛异常而没有最终助手消息。应留下可查询的终态与已知事实，两个 TPS 均为 `null`，已测 TTFT 保留。记录写入失败时，业务结果或原始业务错误保持不变。

8. **并发与重复事件。** 让两个调用在同一毫秒开始并交错输出，验证来源、模型、usage、首尾时间不串用且两条记录都保留。重复终止通知及会话事件重放不重复记账；已完成记录不会被另一调用的收尾覆盖。

9. **覆盖接线。** 通过现有调用入口或其最高可行服务端工厂，验证持久化会话、翻译、自动起名、压缩/摘要均实际接入采集；不能仅证明通用包装器工作就宣称所有业务已覆盖。子代理、定时任务和频道共享路径可用参数化样本验证来源与用途。模型连接测试不产生本功能的记录。这些样本复用同一受控 SDK 边界，不为每个调用方另造内部测试接口。

10. **数据库升级和查询契约。** 从旧 schema 和旧行开始，在临时数据库上重复执行初始化/迁移，验证旧行不丢失、新字段为 `null`、新行可读写、既有计费汇总不重复。验证默认时间范围、会话筛选、默认与最大分页、稳定排序和 `total`。覆盖无持久化会话的辅助调用，确保不被查询或存储约束排除。

11. **运行约束。** 测试使用临时目录与环境变量覆盖，所有 SDK 调用受控，不读取真实用户数据、密钥或访问真实模型。现有 Vitest 全局 setup 会尝试确保隔离实例可用，进程内测试本身无需服务；执行时必须显式处理这一差异，选择不触发服务启动的测试配置。遵守仓库不擅自启动服务的约定，不运行构建。实现完成后运行匹配范围的 TypeScript、ESLint 和上述测试，并如实说明未进行的真实服务商 smoke test。

12. **测试边界确认。** 本 spec 提议以第 1 项作为主要验收边界，附以真实迁移样本和少量调用入口接线样本；没有把浏览器 UI 或真实服务商作为验收依赖。按 to-spec 流程，将这份已写出的具体测试边界交给用户确认，不再重新开展需求访谈。

## Out of Scope

- 修改聊天里的估算 token 数、实时 `t/s`、完成后的展示，或 Token 审计面板视图。
- 流式过程中持续提供实时精确 TPS、逐 token 计时或滑动窗口速率。
- 模型连接测试纳入业务调用统计。
- 按模型、服务商或来源汇总 TPS，均值、加权均值、百分位、排行榜或性能告警。
- 新增按模型、服务商或来源的查询筛选参数。
- 将每个 HTTP 请求尝试的 TTFT/TPS 与逻辑调用建立新的关联和查询体系。
- 从历史记录、字符数、tokenizer 估计值或回合耗时回填这三个指标。
- 单独计算可见正文 TPS 或隐藏思考 TPS。
- 测量服务商内部排队、prefill、逐 token 解码或内部真实生成速度。
- 扩展现有计费汇总的业务覆盖范围，或修复与本功能无关的审计问题。
- 恢复已移除的功能、新增浏览器测试框架、增加外部遥测平台或强制进程终止后的调用恢复。

## Further Notes

- 本 spec 来自两轮 grilling 的既定选择：全部业务调用、逻辑调用粒度、首个有效输出、服务端持久化和逐调用 API；全部 output token、首尾有效输出窗口、异常样本不计算 TPS、暂不提供汇总。
- “准确”指 token 数依据服务商实际报告，时间依据 Pi Work 服务端观测。服务商未报告或 SDK 无法可靠区分的事实不能由 Pi Work 凭空补齐。
- 输出流通常按 chunk 而非逐 token 到达。短回复或分块稀疏时生成 TPS 波动较大；本次仅对无效窗口返回 `null`，不另加未经讨论的最短窗口或最少 token 门槛。
- 隐藏思考可能计入输出 token，但没有对应增量。因此平均生成 TPS 的分子可能含首个可见增量之前生成的 token，数值可能偏高；用户已接受统一使用全部输出用量。这一指标不得被表述为隐藏思考与正文一致可观测的内部生成速度。
- SDK 消息时间戳实际表示请求开始，现有部分注释把它称为完成时刻，这是已核实的文档错误。既有 LLM API 审计耗时截止响应头，不能改称 TTFT；既有回合耗时还包含工具等操作，不能直接作为模型调用耗时。
- 现有 Token 审计逐调用查询尚未被面板视图消费，本次 API 契约必须通过自动化测试明确保障，不能依赖 UI 间接验收。
- 遵守现有领域约定：回合不等于一次助手响应；模型调用的完成不能修改回合等待彻底结束的规则。遵守 ADR-0003 的可测试关切边界、ADR-0004 的回合执行语义，以及 ADR-0005 对 provider 真值和本地估算的区分。
