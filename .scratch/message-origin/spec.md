# Spec：识别用户消息的来源并在 UI 呈现

## Problem Statement

Pi Work 会话里的用户消息，用户无法分辨它是从哪里发进来的。网页端手动输入、微信频道转发、定时任务触发、子代理会话手动补输入——这四种入口写进会话的用户消息在界面上长得一模一样：同一个头像、同一个昵称。当一个频道绑定的会话同时被人在网页里操作、或一个定时任务留下的会话被回头翻看时，用户分不清「这句话是谁说的」，也就无法正确理解这段对话的上下文。

## Solution

给每条用户消息打上「消息来源（Message origin）」标记，并在聊天界面的消息头部按来源渲染：

- **网页端**发送：维持现状——用户头像 + 昵称；
- **频道**转发的入站消息：频道图标 + 频道名；
- **定时任务**触发：定时任务图标 + 任务名；
- **子代理会话**手动补输入：机器人图标 + 父会话标题。

没有标记的消息一律视为网页端发送，所有历史消息自动兼容。来源是**每条消息**的属性，不是会话的属性：频道绑定的会话随时可能被人在网页里手动输入，只有 per-message 才永远准确。

## User Stories

1. 作为网页端用户，我希望自己手动输入的消息显示我的头像和昵称（与现状一致），所以我不需要学习任何新东西。
2. 作为网页端用户，我希望历史消息（在本功能上线前发送的）继续显示头像和昵称，所以升级对我来说是无感的。
3. 作为网页端用户，我希望看到某条消息来自微信频道（频道图标 + 频道名），所以我能一眼分辨哪些话是我打的、哪些是别人从微信发进来的。
4. 作为网页端用户，我希望看到某条消息来自某个定时任务（任务图标 + 任务名），所以我能理解这条指令是机器按计划发出的，而不是有人手动输入的。
5. 作为网页端用户，我希望在子代理会话里看到我手动补输入的消息显示机器人图标 + 父会话标题，所以我能记住「这个会话是父会话派生出来的子代理」。
6. 作为网页端用户，我希望悬停在来源标识上看到完整说明（如「来自频道 XX」「来自定时任务 XX」「来自会话 XX」），所以界面保持简洁的同时信息可按需获取。
7. 作为网页端用户，我希望重命名频道、重命名任务或重命名会话之后，历史消息上的来源名称不被篡改，所以历史呈现保持忠实。
8. 作为网页端用户，我希望删除某个定时任务之后，它过去触发的消息仍能显示任务名，所以历史不因实体消失而丢信息。
9. 作为网页端用户，我希望在分支（branch）出来的会话里，来源标识只出现在属于当前分支的消息上，所以呈现与消息树保持一致。
10. 作为网页端用户，我希望上下文压缩（compaction）之后，被压缩掉的来源标记随旧消息一起消失、不留孤儿标记，所以不会出现张冠李戴。
11. 作为从微信频道发消息的人（间接地：作为网页端用户），我希望频道消息进会话后不带任何额外前缀或标记文本，所以模型收到的 prompt 与现在完全一致，对话质量不受影响。
12. 作为定时任务的配置者（间接地：作为网页端用户），我希望任务 prompt 原样进入会话、不带包装，所以任务行为与升级前完全一致。
13. 作为子代理的使用者（间接地：作为网页端用户），我希望手动补输入照常经由任务管理器排队进入子会话，所以补输入的既有规则（忙碌拒绝、并发队列、去重）不受影响。
14. 作为网页端用户，我希望来源标识只影响显示、不进入模型上下文，所以 token 消耗与模型行为零变化。
15. 作为网页端用户，我希望同一个频道里不同的人发来的消息都显示频道名（本轮不区分具体发送者），所以界面规则简单可预期。
16. 作为网页端用户，我希望点击来源标识不需要跳转（本轮），所以不会误触离开当前阅读位置。
17. 作为开发者，我希望消息来源的形状是判别联合、便于将来新增来源种类（如邮件、其他 IM），所以扩展时不改动既有来源的渲染与存储。
18. 作为开发者，我希望「来源 → 图标/文案」的映射是一个纯函数，所以 UI 组件无需包含任何决策逻辑。
19. 作为开发者，我希望审计层的 source/purpose 字段保持原样，所以审计数据与这次改动互不干扰。
20. 作为运维者，我希望 JSONL 里只有非网页来源才写标记行，所以会话文件不会因为本功能而逐条膨胀。

## Implementation Decisions

以下决策已在设计讨论中定案，并记录在 ADR（消息来源用 custom entry 旁路记录）与 GLOSSARY（消息来源词条）中：

1. **领域模型**：消息来源是每条用户消息的属性，用判别联合表示——网页端（无附加数据）、频道（频道 id + provider + 名称快照）、定时任务（任务 id + 名称快照）、子代理会话（父会话 id + 父会话标题快照 + 子会话 id）。id 与名称快照都存：渲染优先用快照（历史稳定、实体可删），id 留作将来的跳转/区分能力。
2. **缺省规则**：没有标记 ≡ 网页端发送。所有历史消息、乐观插入的本地消息天然落进这条规则，无需迁移。
3. **持久化载体**：非网页来源的用户消息写入后，紧跟追加一条 custom entry（customType 为本功能专有），data 含来源本体 + 毫秒时间戳 + 消息文本前 80 字符（仅诊断用，不参与归属判定）。不使用 `custom_message`（会进模型上下文）、不包装 prompt 文本（污染输入）、不用会话级 sidecar（粒度不够）。
4. **归属规则**：custom entry 作为消息树节点挂在它描述的 user message 之后；读取时归属树序上最近的前一条 user message。会话内 turn 串行，无竞争；极小概率 prompt 失败导致错挂只影响显示层。entry 随消息树走：分支自然脱落、压缩随旧分支消失。
5. **写入收口**：所有 prompt 路径（网页 API、频道 inbound、定时任务 runner、子代理手动输入）最终汇聚于同一个 RPC 命令分发点。在该命令上增加可选 origin 字段，由各发送方填好；网页端不传。收口处在派发 prompt 后立刻写 custom entry；只有非网页来源才写。
6. **各发送方的取数**：频道来源从频道的持久化记录取 id/provider/名称；定时任务来源从任务记录取 id/名称；子代理会话来源在手动输入路径上查子会话的父会话归属，父会话标题取发送时刻的快照。
7. **传输与展示**：共享类型里的用户消息增加可选 origin 字段，只存在于 API/SSE 边界，**永远不会写回 JSONL 的消息体**。历史消息由会话读取方在扫描时把 custom entry 合并到消息上；实时消息由 RPC 会话层在发出 message_end 事件时附带 origin。
8. **UI 渲染**：用户消息头部的渲染从写死的用户头像改为按 origin 单点分发：一个 shared 纯函数把 origin 映射为图标 + 名称 + 悬停文案，组件无脑消费，模板只有一套；网页端（含缺省）走现有头像 + 昵称。悬停文案走 i18n 词典机制。
9. **审计层不动**：LLM/Token 审计的 source/purpose 与消息来源是两套概念，本轮不统一、不做映射。

## Testing Decisions

好的测试只断言外部行为（纯函数的输入输出、reader 返回的消息序列），不断言内部调用次数、不 mock 依赖袋。共两个 seam（已在设计确认）：

1. **Seam A —— 纯 shared 函数**：来源的缺省回退（无标记 → 网页端）、origin → 图标/名称/悬停文案的映射、以及「prompt + origin → 待写 entry 数据」的构造规则（时间戳、前缀截断）。先例：`session-title`、`message-content` 的纯单元测试。
2. **Seam B —— reader 读取回环**：在临时数据目录手写会话 JSONL（user message + 紧跟的 origin entry），断言读取结果把 origin 挂到树序最近的前一条 user message；无标记消息不带 origin；分支/压缩场景下 entry 随消息树脱落。先例：`session-read-path`（沙箱目录 + 直调 reader，绝不触碰真实用户数据）。

不测的部分：收口处的写入动作、SSE 附带管道、消息组件的 JSX——决策都在 Seam A 的纯函数里，这些靠 Seam B 回环加手动 smoke test 兜底。

## Out of Scope

- 点击来源标识的跳转（返回值预留跳转目标字段但本轮不填）。
- 区分频道内具体发送者（微信群里谁发的）；联合类型将来可加发送者字段，不改已有形状。
- 新增频道 provider 或其他来源种类。
- 审计层 source/purpose 与消息来源的统一或映射。
- 乐观插入消息的来源标注（网页端乐观插入天然正确；其他来源不经乐观插入路径）。
- 对 pi SDK `UserMessage` 结构的任何修改或向上游提需求。

## Further Notes

- 术语遵循 GLOSSARY「消息来源（Message origin）」词条：per-message 属性、无标记 ≡ 网页端、不与审计 source/purpose 混用。
- 持久化取舍的完整理由见 ADR（消息来源用 custom entry 旁路记录）：pi SDK 的 `UserMessage` 没有元数据字段是直接动因；若上游将来给 `UserMessage` 增加元数据能力，该决策可重估。
- `custom_message` entry 在本仓库零引用，本轮也保持零引用。
- 实现完成后按仓库惯例运行 TypeScript 检查、ESLint 与单元测试；涉及流式事件，补充手动 smoke test（网页发送、频道消息、定时任务触发、子代理补输入四条路径各验一次显示）。
