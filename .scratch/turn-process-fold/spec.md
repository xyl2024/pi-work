# 回合过程折叠：分页展开

`Status: ready-for-agent`

## Problem Statement

聊天里每一个已完成的回合，中间过程（思考块、工具调用、工具调用之间的文本）都被压成一行摘要，例如「34 条消息 · 12 次工具调用 · 3× bash, 2× read」。这一行只有两个极端：完全收起，或者一次摊开整轮。

于是就出现了两个都不好用的场景：

- 想看「刚才那几步到底做了什么」，点开就得滚动几千像素，`34` 条消息里的 30 条与当前疑问无关；想回到摘要行还得往上滚很久。
- 想看完整的执行过程，又必须先看完前面几十条已经知道的步骤，没法直接从最近几步开始读。

摘要行本身还有两个问题：它只有「全部」一个含义，用户无法在「最近几步」这个最常用的粒度上操作；摘要行左侧那个 chevron 是唯一的交互提示，而「展开」这件事没有第二档可选。

## Solution

把摘要行从「开/关」改成「按页展开」，页大小 5 条：

- 悬停（或键盘聚焦）在摘要行上时，行的右端出现两个按钮：「展开最后 5 条」与「展开全部」。鼠标点击正文不再意外触发展开。
- 点「展开最后 5 条」，只显示本轮最后 5 条过程消息；若本轮不足 5 条，等同于全部展开。
- 已经是部分展开时，按钮变成「再展开 5 条」与「展开全部」；剩余不足 5 条时只留一个「展开剩余 3 条」。
- 只要这一轮处于「展开了」的状态（部分或全部），点击摘要行就折叠回一行。
- 摘要行始终告诉你现在看的是哪一段：部分展开显示 `10 / 34 条消息`，工具调用统计跟着当前窗口走。
- 展开与折叠不做「内容跳一下」：首次展开在摘要行下方长大；继续往上翻（部分 → 更多）时补上滚动偏移，让正在读的那几条原地不动。

右下角的「全部折叠」按钮仍然是跨轮的全局操作，把每一轮归零到收起。

## User Stories

1. 作为用户，我想在摘要行上看到「展开最后 5 条」这个入口，这样我能从最近几步开始读，而不是跳过整轮。
2. 作为用户，我想在摘要行上同时看到「展开全部」，这样当我确实要看全流程时不用点好几次。
3. 作为用户，我想让这两个按钮只在我悬停到摘要行时出现，这样消息正文看起来不会到处是按钮。
4. 作为用户，我想让悬停区只有摘要行这一行，这样我划过正文时按钮不会反复闪现、也不会挡住内容。
5. 作为用户，我想让摘要行在键盘聚焦时也显示按钮，这样我不用鼠标也能用这个功能。
6. 作为用户，我想让摘要行右侧那个 chevron 一直可见，这样我一眼知道这一行可以点。
7. 作为用户，我想点摘要行就展开最后 5 条，这样不悬停也能用主路径。
8. 作为用户，我想在本轮不足 5 条过程消息时，点一次就展开全部，因为「最后 5 条」在这里没有意义。
9. 作为用户，我想在部分展开时看到「再展开 5 条」，这样我可以继续往前翻，而不是直接摊开全部。
10. 作为用户，我想在部分展开时仍然看到「展开全部」，这样看到一半决定「就这样吧，全给我」时不用点四次。
11. 作为用户，我想在剩余不足 5 条时只看到一个「展开剩余 3 条」，这样我不会在两个结果相同的按钮之间做无意义选择。
12. 作为用户，我想在全部展开后不再看到「展开」按钮，这样界面上没有点了没反应的控件。
13. 作为用户，我想在部分展开时点摘要行就折叠回去，这样「点一下就收起」的直觉在两种展开态下都成立。
14. 作为用户，我想在全部展开时点摘要行就折叠回去，这样收起永远是一次点击。
15. 作为用户，我想在部分展开时看到 `10 / 34 条消息`，这样我知道自己看的是哪一段、还有多少没看。
16. 作为用户，我想在收起时看到 `34 条消息`（不带分数），这样收起状态先给我总量、不塞一个 `0 / 34`。
17. 作为用户，我想在全部展开时也看到 `34 条消息`，这样两个「看全了」的状态文案一致。
18. 作为用户，我想让工具调用统计跟着当前窗口变，这样「10 / 34 条消息 · 4 次工具调用」描述的是我正看着的这一段，而不是整轮。
19. 作为用户，我想在收起时看到整轮的工具调用统计，这样摘要行仍然是这一轮最有信息量的那一行。
20. 作为用户，我想在点「再展开 5 条」时让正在读的内容原地不动、新内容出现在它上方，这样我的视线不被推走。
21. 作为用户，我想在首次展开时让内容在摘要行下方出现，这样展开方向和现在的折叠组一致，不需要重新学。
22. 作为用户，我想在小规模插入时保留高度过渡动画，这样展开有一点手感。
23. 作为用户，我想在大规模插入（比如一次摊开 30 条）时不做高度动画、直接到位，这样我不用等一个没有信息量的滑动过程。
24. 作为用户，我想让「再展开 5 条」与「展开全部」在往上插内容时都不做动画并保持锚点，这样补偿和动画不会互相打架。
25. 作为维护者，我想让「部分展开 → 更多」的滚动补偿只在需要的方向上发生（内容插在已渲染内容之前），这样首次展开不会莫名其妙往下跳。
26. 作为用户，我想让这一轮的展开状态在我切到别的会话标签页再切回来时还在，这样来回对比时不会每次都重新点。
27. 作为用户，我想在重开会话后看到折叠组回到收起，因为那是默认态。
28. 作为用户，我想让每轮的展开程度互相独立，这样展开第 3 轮不会顺带摊开第 7 轮。
29. 作为用户，我想在 agent 正在跑别的回合时，仍然能展开历史上的某一轮，这样我不被一个全局禁用挡在外面。
30. 作为用户，我想在 agent 跑当前回合时看到的过程仍然内联流式显示（不出现折叠组），这样流式体验不变。
31. 作为用户，我想让右下角「全部折叠」把部分展开的轮也归零到收起，因为那就是它的字面意思。
32. 作为用户，我想在点击「全部折叠」之后，各轮内部的思考块 / 工具卡片仍然保留我之前的手动展开状态，这样全局按钮不会重置我的阅读位置。
33. 作为用户，我想在触屏上也能用到「展开最后 5 条」，这样没有 hover 的设备不会只剩一个入口。
34. 作为用户，我想让新增的按钮文案跟随界面语言，这样中文界面里不会混进英文。
35. 作为维护者，我想让页大小（5）成为一个可改的常量而不是散落在文案里，这样以后调步长只改一处。
36. 作为维护者，我想让折叠状态机是可测试的纯函数，这样「剩余 3 条」「全部展开时点行」这类边界靠测试钉住，而不是靠手点。
37. 作为维护者，我想让「窗口切片」和「摘要计数」也在这套纯函数里，这样组件只负责渲染和鼠标事件。
38. 作为维护者，我想让组件接收「条目数组」而不是预先渲染好的整段子节点，这样「只渲染最后 5 条」在组件内有明确位置，而不是把每轮的展开数字搬回聊天窗口。

## Implementation Decisions

**新增一个纯 module：`lib/shared/process-fold.ts`，它承载整个特征的全部规则。** 状态、事件、窗口切片、摘要计数都在这里，不引入 React、DOM 或 `lib/server`（与 `chat-timeline`、`panelTabs`、`scroll-follow` 同一个层级与风格）。组件不自己判断「还剩几条」。

状态与事件的形状（这是本次设计里唯一需要精确固定的接口，直接作为实现契约）：

```ts
export const PROCESS_FOLD_PAGE = 5;

/** collapsed = 只有摘要行；partial = 只看最后 N 条；full = 全部。 */
export type ProcessFoldState =
  | { readonly kind: "collapsed" }
  | { readonly kind: "partial"; readonly shown: number }
  | { readonly kind: "full" };

export type ProcessFoldEvent =
  | { readonly type: "row-click" } // 点摘要行
  | { readonly type: "reveal-next" } // 点「(再)展开 5 条」
  | { readonly type: "reveal-all" } // 点「展开全部」
  | { readonly type: "collapse-all" }; // 右下角「全部折叠」广播

/** total = 本轮可显示的过程消息条数。 */
export function nextProcessFold(
  state: ProcessFoldState,
  event: ProcessFoldEvent,
  total: number,
): ProcessFoldState;
```

转移规则（实现即这张表）：

- `row-click`：`collapsed` → 优先页（`total <= PAGE ? full : partial(PAGE)`）；`partial` → `collapsed`；`full` → `collapsed`。
- `reveal-next`：`collapsed` → 同 `row-click`；`partial(n)` → `partial(n + PAGE)`，但若 `total - n <= PAGE` 则直接 `full`；`full` → 不动。
- `reveal-all`：任何非 `full` → `full`；`full` → 不动。
- `collapse-all`：任何状态 → `collapsed`。
- `total === 0` 时始终 `collapsed`（理论上组不会渲染，防御性归一）。

窗口与摘要：

```ts
/** 当前状态要渲染哪一段：数组下标区间 [start, end)，以及摘要行需要的数字。 */
export function processFoldWindow(
  state: ProcessFoldState,
  total: number,
): {
  start: number;
  end: number;
  /** 摘要行显示的消息数字（收起时 = total）。 */
  shown: number;
  /** true 时摘要行渲染 `{shown} / {total}` 形式。 */
  isFraction: boolean;
  /** true 时窗口内容插在已渲染内容之前（需要滚动补偿）。 */
  insertsAbove: boolean;
};
```

- 收起：`start = end = 0`，`shown = total`，`isFraction = false`。
- 部分：`start = total - n`，`end = total`，`shown = n`，`isFraction = true`。
- 全部：`start = 0`，`end = total`，`shown = total`，`isFraction = false`。
- `insertsAbove`：仅当「上一状态已渲染过内容」（`partial` → `partial` / `partial` → `full`）为 true。它由调用方用旧状态比较得出，纯函数另给一个 `foldInsertsAbove(prev, next, total)` 或由组件自己持有上一状态判断——实现时选一处，不要两边都算。

**摘要计数跟随窗口，收起时跟随整轮。** 工具调用统计（名称分组 + 次数）对当前窗口内的条目求和；收起时窗口为空，此时回退为整轮求和（摘要行是那唯一的信息载体）。这条规则进纯 module（`summarizeFoldWindow`），组件不写 `if (collapsed)`。

**`ProcessDetailsGroup` 的输入从 `children` 改成条目数组。** 现在它收 `{ messageCount, toolCallCounts, children }`，无法只渲染后 5 条。改成收 `items: { key: string; node: ReactNode; toolCalls: Record<string, number> }[]`：`ChatWindow` 继续拥有「哪些消息进组、进组的每一条渲染成什么」这一知识（它已经用 `countToolCallsByName` 统计单条），组件拥有折叠状态、悬停、滚动补偿与切片渲染。`messageCount` / `toolCallCounts` 两个 prop 由 `items` 派生，删除。

**悬停与聚焦的范围锁在摘要行。** 悬停触发区是摘要行这一行的宽度范围（不是整个折叠组的高度），按钮在行内右端排列，不浮动覆盖正文。触发条件为 `group-hover` + `group-focus-within`。chevron 常驻可见，旋转表示「已展开」。

**点击语义只有两条**：未展开 → 展开第一页；已展开（部分或全部）→ 收起。展开程度只由按钮推进。

**滚动补偿只发生在内容插到已渲染内容之前时。** 首次展开（`collapsed` → `partial`/`full`）内容在摘要行下方生长，交给浏览器默认行为；`partial` → `partial` / `partial` → `full` 时在插入瞬间补偿滚动容器的 `scrollTop`，让用户正在读的第一条保持原位。仓库目前没有任何 `overflow-anchor` 覆盖，因此这条补偿必须显式实现，不能指望浏览器。

**动画规则与上面同源：插在下方且插入高度未超过阈值（约 600px）才做 `height` 过渡；凡是往上插的转移一律不做过渡、直接落位 + 补偿。** 现有折叠容器的高度过渡由 `useCollapseHeight` 的 ResizeObserver 驱动，内容一变就重新触发动画，与逐帧补偿天然冲突，所以两类路径必须分开。

**新增文案走现有 i18n 机制**（`lib/shared/i18n-dict/`），键为英文、中文在对应字典里；页大小写成常量 + `{n}` 占位符，不把 `5` 写进文案。新增键至少覆盖：「展开最后 {n} 条」「再展开 {n} 条」「展开剩余 {n} 条」「展开全部」「{n} / {total} 条消息」。现有 `"{n} messages"` / `"{n} tool call(s)"` / `"{n}× {tool}"` 继续复用。

**右下角「全部折叠」的契约不变**：仍然是一次性 nonce 广播，组件收到后把折叠状态归零到 `collapsed`，但不碰组内子块（思考块、工具卡片）的手动展开状态。

**`agentRunning` 只约束全局「全部折叠」按钮，不约束历史回合的折叠组。** 历史回合不参与流式，展开它们不会与到达的块竞争。

**折叠状态住在组件内 `useState`**：切会话标签页保留，重开会话 / 重载丢失（回到收起）。不引入 tab 级 store。

## Testing Decisions

**唯一的新测试缝是 `lib/shared/process-fold.ts` 这个纯 module。** 不为组件引入新的渲染测试设施：组件只做「把纯函数的返回映射成 DOM + 鼠标事件 + 滚动写操作」，它自己的正确性靠人工 smoke（悬停出现按钮、点击后滚动是否稳定、动画是否只在预期路径出现）。

好测试的标准：只断言外部行为——「给定状态 + 事件 + 总数，下一状态是什么」以及「给定状态 + 总数，渲染窗口的区间与摘要数字是什么」。不断言内部字段命名、不测 React 组件的 DOM 结构、不测动画与滚动像素（那属于 smoke）。

要覆盖的边界至少包括：

- `total` 为 0 / 1 / 4 / 5 / 6 / 10 / 11 / 34 时的首点行为（不足一页等同全展开）。
- `partial(n)` 上 `reveal-next` 在剩余 > 5 / == 5 / < 5 三种情形下的落点。
- `partial` 与 `full` 上 `row-click` 都回到 `collapsed`；`collapsed` 上 `row-click` 进第一页。
- `collapse-all` 从三种状态都回到 `collapsed`。
- 窗口切片：`partial(5)` 于 `total=34` 得 `[29, 34)`；`partial(5)` 于 `total=3` 归一为整段。
- 摘要计数：窗口内求和、收起时回退整轮、空窗口不产生 `0 次工具调用` 这种噪音。

先例：`tests/unit/chat-timeline.test.ts`（纯投影模块的状态与索引断言）与 `tests/unit/scroll-follow.test.ts`（决策表式断言）就是这套写法的样板；新测试放 `tests/unit/process-fold.test.ts`。

## Out of Scope

- 组内子块（`ThinkingBlock` / `ToolCallBlock`）展开状态在整组折叠后是否保留：现状是折叠即卸载、状态丢失，本次不改，明确接受。
- 组内虚拟化、按需懒渲染、`full` 状态下的分批自动加载：先直接挂载，出现具体卡顿再单独处理。
- 当前正在流式输出的回合：它本来就不生成折叠组（内联在流式视口里），交互不变。
- 右下角「全部折叠」按钮的位置、图标与禁用逻辑：保持不变。
- 触屏专用手势、双击展开、滚轮展开等额外入口。
- 折叠组摘要行的视觉重设计（字体、间距、配色）：沿用现有 `process-summary` 样式，只加按钮。
- 会话内搜索在折叠组内的命中跳转行为：沿用现状（命中项仍会被展开/高亮），本次不调整规则。

## Further Notes

- 词汇：这个特征在对话里被叫作「回合过程折叠」——一个**回合**（Turn）的中间过程被折成一行摘要，现在支持按页展开。若实现时需要在 `CONTEXT.md` 里登记，建议加一条「回合过程折叠（Turn process fold）」，指向 `lib/shared/process-fold.ts`，并说明它和「对话时间线」的分工：时间线决定「渲染哪些消息行」，它决定「一行摘要里展开哪一段」。
- 页大小 5 是产品参数，不是性能参数；它同时决定了「不足 5 条就全展开」这条退化规则。
- 摘要行从「一个纯展示元素」变成「一行带两个按钮的交互行」，实现时注意它不能用一个 `<button>` 包住两个按钮（现在的实现是 `<button>` + 内容，需要改成带 `onClick` 的 `div` + 行内按钮，键盘可达性由 `tabIndex` / `role="button"` 与子按钮共同承担）。
